## 우선 검증: 기존 변경사항
1. 작업 브랜치와 최신 `main`, Android 브랜치를 diff로 비교하고 다른 진행 중 변경을 손실 없이 통합한다. 각 브랜치의 변경은 임의로 덮어쓰지 않는다.
2. 모바일 360/390/412/430px에서 차트가 실제 표시되는지, 차트와 매수·매도 버튼을 가급적 동일 화면에서 볼 수 있는지 확인한다. CSS `.chart-dark`·`#chart`·`.chart-panel`에 기존 높이 동기화 스타일이 있으므로 우선순위/resize observer 영향 검사. 190px은 1차 값이며 가독성 부족 시 180~220px 내에서 기기별 조정.
3. 기존 매매/신용 0~300%, 신용 지정가/시장가, 담보/반대매매, 긴급자금대출, 수수료, 지정가 예약·취소·부분체결·자동 청산, 현금 결제 검증. `ledger-v2.js`에서 일반 매도와 강제 매도 모두 **신용 수량 우선** 소진, 그에 해당하는 신용 원금·비용 비례 차감, 잔여 일반주식 및 잔여 채무의 일관성 검사. 예: 일반 30주+신용 70주 보유 후 50주 매도 => 신용 20주+일반 30주, 총 50주 잔존.
4. `game.js`에서 신용매도 제거 후 이벤트에 null 참조가 없는지 확인; 불필요한 import `executeCreditSale` 등 정리. 웹과 Android가 같은 최신 소스 사용하도록 동기화.
5. 기존 문서에 3판 후 전면광고라는 과거 계획이 있음. 이 요구에서는 **하루 5판 무료 + 6판부터 보상형 광고**로 수정. 과거 규칙과 이중으로 광고가 발생하지 않도록 별도 전면광고 정책은 적용하지 않는다.

## P0: 차트를 보며 즉시 주문하는 모바일 UX

- 차트 하단에 주문하기가 바로 이어져야 하며 호가 영역은 별도 접기/탭 또는 주문 옆 보조영역. 화면 폭이 작아도 버튼/수량 입력의 터치 영역과 가독성 보장. 320/360/390/412/430px 및 세로/가로·안전영역·키보드 표시 검증.
- 가능하면 차트 상단/주문 하단을 한 화면 안에서 함께 볼 수 있게 하고 스크롤을 강제하지 않는다. 데스크톱 3열 UX 유지.
- 최소화한 통계는 삭제하지 않고 필요할 때 볼 수 있어야 함. 차트 갱신/터치·호가 선택 후 지정가 입력/매수매도 동작 유지.

## P0: 신용매수/긴급자금대출/광고 문구
- 웹과 모바일에서 사용자에게 표시되는 '신용거래'는 '신용매수'로 통일(팝업·가이드·버튼·피드백·접근성). '긴급자금대출광고'처럼 광고를 메뉴명에 넣지 않고 '긴급자금대출'만 표시. 기능 진입 시 수동 '신용매도 수량 ~주 / 최대 수량 / 신용매도 확정' UI 없음.
- 신용은 일반 '매도' 주문 시 신용 보유분부터 자동 매도 정산한다. 신용채무·긴급자금대출 상환 순서 및 순자산 계산은 기존 회계 규칙을 보존하며 회귀 테스트 추가.
- '보상형 광고 1회', '이번 판에만 적용', '광고 없이 이용 가능' 같은 내부 정책성 설명은 UI에 표시하지 않는다. **실제 광고 이용이 필요한 경우에만** 버튼이나 모달에 '광고 보고 이용하기'와 보상 내용을 간략 표시. 광고 완료 전 기능을 지급하지 않는다.
- 현재 `main`의 웹 `index.html`은 `body data-test-tools="enabled"`로 테스트 활성화, 기존 `game.js`는 `testTools`에서 기능을 직접 해제함. 따라서 웹의 현재 동작은 실광고 보상 검증 결과가 아님. Android AdMob 실제 탑재·광고 단위 및 테스트기기 설정 확인 전 실광고로 단정하지 말 것. 개발 시 Google 공식 테스트 광고 ID 사용, 운영 전 실광고 ID 교체. 광고 없는 테스트 경로가 배포 운영에서 남지 않도록 분리.

## P1: 하루 5판 + 보상형 광고로 추가 플레이
- KST (`Asia/Seoul`) 기준 매일 00:00:00~23:59:59, **하루 처음 시작한 판부터 무료 5판**. '다시하기', '한 번 더 하기', 중도 재시작도 **새 판이 시작되면 1판 차감**. 단순 일시정지/복귀/앱 재실행 후 기존 판 이어하기는 새 판 아님. 판 시작 원자 처리하여 중복 차감 방지.
- 5판까지는 광고 없이 진행. 6판째부터 '광고 보고 더하기' -> 완료된 실제 보상형 광고 1회당 **추가 1판** 권한 획득. 광고 중단/실패/미준비/네트워크 오류 시 권한 미지급. 여러 번 눌러도 이중 지급 금지. 전면/배너광고를 시청 보상으로 간주하지 않음.
- 홈/결과 화면에 '오늘 남은 무료 플레이 N/5' 표시; 한도 소진 시 '광고 보고 한 판 더' 버튼. 사용자가 광고를 취소하면 안전하게 이전 화면 유지. 기기 날짜 변경/저장소 삭제/재설치로 우회되지 않도록 가능하면 서버 기준 시간과 계정·익명 사용자 ID를 이용한 서버 확인. KST 자정 경계, 중복 탭, 오프라인 복귀, 여러 기기 동시 실행 시험.
- AdMob 보상형 광고 확인은 **검증된 reward 이벤트 이후**에만 제공. 서버 측 SSV를 쓰면 권장; 웹은 별도 지원 광고 제공자/정책과 호환성을 확인해 설계. 광고가 로드되지 않을 때 유저에게 오류를 설명하고 기존 무료 5판에는 장애를 주지 않는다.

## P1: 최초 닉네임 및 전체 공개 일일 TOP5 2종
- 최초 시작 시 닉네임 등록(2~12자, 한글/영문/숫자/밑줄 허용, 앞뒤 공백 제거, 금칙어/중복검사, 길이 검사). 기기·계정 연결은 Android 앱과 웹에서 모두 작동하도록 설계. 로그인 없는 익명 인증도 가능하나 재설치/다른 기기 복원 제한을 명시하거나 추후 계정 연동 옵션 마련.
- 전 유저가 읽을 수 있는 **일일 단타왕** 두 섹션: (1) 수익률 상위 5명, (2) 수익금 상위 5명. 당일 완료한 유효한 판 중 **개인별 최고 성적 하나**를 각 지표에 독립적으로 반영. 같은 닉네임/사용자가 여러 판으로 한 랭킹을 도배하지 못하도록 user_id별 최고 1건. 서로 다른 최고 판이어도 됨.
- 수익률 = (최종 순자산-초기 순자산) / 초기 순자산 × 100; 수익금 = 최종 순자산-초기 순자산. 기존 1억원 가상 시작금을 기준으로 신용·긴급자금 채무·수수료·청산을 반영한 **게임 최종 확정값** 사용. '장중 최고 수익률'이 아니라 **5분 종료 확정 순수익률** 기준.
- 서버 시각 KST 날짜, 동점 시 먼저 기록한 시각 순(후속 user_id 안정 정렬). 랭킹: 순위, 닉네임, % 또는 가상 원 금액, 해당 일자. 1~5위만 공개, 개인 식별 정보/기기 ID 노출 금지. 사용자 닉네임 수정·신고/삭제 절차 제공.
- **클라이언트가 제출한 임의 수익액을 그대로 믿지 않는다**. 초기 단계에는 서명된 세션/서버시드+거래 이벤트 재현검증/비정상 결과 거부, 속도제한, 중복 방지, 권한검사 등으로 방어. 검증 불가 점수는 랭킹에서 제외. 모든 유저가 동일 규칙을 적용받도록 게임 버전도 기록.

## 최소 비용 백엔드 및 iMac M1
- **권장: Cloudflare Pages(기존 정적 웹) + Supabase 무료 등 관리형 DB/Auth(공식 사용량·정책 확인 후 선택) + iMac 보조 서버**. DB에 profiles(user_id, nickname), daily_play_quota(user_id, kst_day, free_started, bonus_credits), sessions(id,user_id,day,status,game_version,seed,...), verified_scores(session_id,user_id,rate,profit,verified_at) 저장. RLS 및 최소 권한 서버 RPC/API를 통해 quota/점수 처리. 브라우저에 service-role 키 절대 포함 금지.
- 구조: Android·웹 -> HTTPS API -> DB. 읽기용 daily TOP5는 캐시 가능, 앱에서 짧은 주기로 갱신/수동 새로고침. 서버 5판 제한과 성적 등록은 원자적 트랜잭션, idempotency key, 인증 검사. 인덱스(user_id, day), (day, rate), (day, profit). 필요한 경우 edge function.
- **iMac M1은 백업/모니터링/관리/배치 재검증에 적합**, 절전·정전·주거용 인터넷/NAT/동적 IP 때문에 단독 랭킹 원본 서버로 권장하지 않음. iMac이 꺼져도 사용자 랭킹은 DB와 API에서 계속 제공되도록 설계. Tailscale은 관리자 접근용, 공용 유저 API를 Tailscale 전용으로 만들지 않음. 민감한 DB 키는 iMac의 환경변수/키체인에만 보관.
- 초기 유저 수가 적다면 운영비 0원 목표는 가능하지만 영구 무조건 무료 보장은 금지. 무료 할당량/휴면 정책/광고 규정 확인. 데이터 백업은 iMac에 암호화 일별 저장, 복구 테스트. DB 장애 때 이전 랭킹 읽기 캐시는 가능하지만 점수 제출을 성공 처리하지 않는다.

## Android Google Play 이미지 01 / 실제 설치 아이콘 일치
- Play Console의 실제 '01번' 원본 파일이 어떤 사진인지 **소스/콘솔에서 확인**. 임의 새 디자인 금지. 스토어 대표 이미지/스크린샷 01과 기기에 표시되는 런처 아이콘은 규격 및 용도가 다르므로, '동일해야 하는 이미지'가 아이콘인지 시작화면인지 앱 내부 이미지인지 먼저 구분하여 **지정된 동일 원본 디자인/텍스트/색상** 사용.
- 기존 `codex/scalping-king-android` 작업의 `scalping-king-android/store-assets`, Android adaptive icon foreground/background/monochrome, mipmap, roundIcon, splash, `android/app/src/main/assets/public` 내 복사된 이미지 등을 체크. Android는 `npm ci`, `npm run android:sync`로 최신 웹 파일을 다시 반영 후 APK/AAB 재빌드. 설치 앱의 오래된 캐시·구버전 APK·versionCode 확인.
- 실제 Play Console 등록 이미지는 GitHub에 없을 수 있음. 해당 원본을 확보하지 못하면 변경을 추정해서 진행하지 말고 누락 사항을 보고. 스토어 스크린샷은 실제 최신 웹앱 화면을 바탕으로 촬영·제작하고 사용자 요청대로 표현/문구 무단 변경 금지.
- Google Play / AdMob 정책을 다시 점검. '모의투자 게임'임을 명확히 표시.

## C. 신용매수와 자동 매도
1. 모바일·웹·Android 화면의 '신용거래' 버튼·팝업·설명·알림을 모두 '신용매수'로 통일. '긴급자금대출광고' 표기는 '긴급자금대출'로 바꾸되 기능 잠금 해제 방식은 기존 정책/신규 광고 연결에 따름.
2. 신용매수 창의 '신용매도 수량 ... 주 / 최대 수량 / 신용매도 확정' 요소와 연결 이벤트 삭제. 신용 시장가·지정가 선택과 투자비율 0~300%, 대출·담보 위험 표시 및 매수 확정 유지.
3. **일반 매도 버튼 하나**로 모든 매도를 처리한다. 체결한 수량만큼 해당 종목의 신용 보유분을 먼저 매도 정산하고, 남는 부분은 일반 보유분에서 차감. 신용 원금·원가 비례 차감, 수수료, 순자산, 잔여 주식, 담보비율, 긴급자금대출 상환 규칙을 일관되게 유지. 미체결 주문에서는 체결 전 수량 차감하지 않음.
4. 예: 일반 30주 + 신용 70주 보유, 50주 매도 완료 -> 일반 30주 + 신용 20주 잔존. 20+30으로 부분체결해도 동일. 신용 전량 매도 시 creditQty/연결 원금 0. 로스컷·반대매매·VI·지정가 예약·취소/정정·일반/신용 혼합·긴급자금대출 상환까지 자동 테스트 추가. 미검증 회계 변경을 운영에 바로 병합하지 않는다.

## D. 사용자에게 보이는 광고 문구와 보상
1. 사용자에게 내부 광고 잠금 정책('보상형 광고 1회', '이번 판에만 적용', '광고 없이 이용 가능')을 표시하지 않는다. 다만 실제 광고가 필요한 경우에는 사용자에게 **'광고 보고 이용하기'**와 얻는 보상을 명확하게 고지하고 동의 후 재생한다. 광고를 무단·무고지 재생하지 않는다.
2. 웹의 \`data-test-tools="enabled"\`는 테스트 우회 경로다. 이를 실제 광고 송출의 증거로 간주하지 않는다. Android AdMob 테스트 광고 및 실제 운영 ID를 분리하고 사용자 실기기에서 검증. 웹에서는 AdMob Android SDK를 그대로 호출할 수 없으므로 웹용 보상 지원방식을 확인해서 구현; 불가능하면 실제 시청을 가장하지 않고 웹 지원 여부를 보고.
3. 보상 지급은 제공자가 **검증한 완료 이벤트**에만 의존. 닫기/취소/로딩 오류/백그라운드 전환/네트워크 실패 시 미지급. 가능한 서버측 광고 보상 검증(SSV, 서명·트랜잭션 ID)을 사용하여 중복 지급 방지. 광고 중 게임 타이머·시세 정지, 종료 시 정확히 복귀.
4. 과거 계획에 있는 '3판 종료 후 전면형 광고'는 이번 명세의 **무료 5판 이후 보상형 광고로 추가 시작**과 충돌하므로 제거/중지. 별도 배너가 있더라도 플레이 횟수 보상과 혼동하지 않는다.

## E. 일일 5판과 다시하기 — 정확한 판수 정의
1. 날짜는 서버가 정한 \`Asia/Seoul\` 날짜, 한국시간 00:00 자정 기준. **무료 시작권은 하루 사용자당 5판**. 첫 플레이·종료 후 다시하기·도중 다시하기·한 번 더 하기 모두 신규 게임 세션 승인 및 생성 시 1판 소비. 일시정지/재개/동일 세션 복원만으로는 소비하지 않는다. 5분 완주 여부와 관계없이 일단 시작된 판은 사용 처리.
2. 6판째부터 버튼 **'광고 보고 한 판 더'**. 완료 검증된 보상형 광고 1건 당 *추가 게임 시작권 1개* 지급. 사용 시 소모. 중복 클릭·중복 callback·재시도에도 광고 이벤트 ID당 1개만 지급. 광고를 봤으나 판 시작 전에 앱이 종료되면 서버에 미사용 보상권 보존. 서버가 판 시작을 승인한 뒤 중도 포기한 경우 환불하지 않는다.
3. UI: '오늘 무료 플레이 0~5/5 사용', '남은 무료 플레이 N회', 미사용 보너스권 N회, 한도 소진 시 광고 버튼. 미로드 광고/취소/검증실패/서버 장애 시 지급 및 시작 차단을 정확히 알린다. '광고 완료' 모의 버튼으로 실서비스 권한 부여 금지.
4. 같은 계정의 웹/Android·여러 기기·동시 탭에서 서버가 단일 원자적 트랜잭션과 멱등키로 quota를 보장. 기기 날짜 변경, 앱 재설치, localStorage 삭제로 하루 제한 우회되지 않도록 서버 기준 카운트. 단 로그인 없는 익명 사용자만으로는 재설치 우회를 완전히 막을 수 없으므로 이를 명시하고 공정한 제한/랭킹이 필요하면 Google 로그인 등 안정적인 계정 복원 방식 마련.
5. 오프라인 유지가 꼭 필요하면 **랭킹 제외 별도 연습 모드**로 분리, 공인 서버 랭킹 게임을 오프라인에서 임의 시작시키지 않는다. 서비스 장애 시 무료/보상 횟수를 클라이언트가 임의 추가하지 않는다.
6. 기존 게임의 \`restartRound()->reset()->start()\` 및 초기 \`start()\` 모든 입구를 서버 startSession 승인 단계로 통합하고 중복 세션 생성 금지. KST 자정, 5번째 무료 시작, 광고 1회 획득, 광고 취소, 앱 종료 후 복귀, 중도 다시하기를 테스트.

## F. 닉네임 및 전체 공개 일일 TOP5 두 종류

4. 서버가 발급한 세션 ID/시드/게임 버전 및 시간과 거래 이벤트를 사용하여 결과를 재현·검증해야 한다. 클라이언트가 전송한 손익 숫자 그대로 저장하거나 클라이언트에 비밀 서명키를 싣는 구현은 금지. 서버에서 결정론적 결과 검증이 기술적으로 불가능하면 **공인 랭킹 출시는 보류**하고 먼저 검증 가능한 게임 엔진 또는 서버 권위 시뮬레이션을 구현. 레이트 리밋, 비정상 기록 차단, 중복 제출 방지.
5. 비회원도 랭킹 열람 가능, 기록 등록은 인증 사용자만. DB/API 오류 시 랭킹을 임의 성공 처리하지 않으며 이전 캐시를 보여줄 경우 최종 갱신 시각 표시.

## G. 서버: 최소비용 Cloudflare Pages + Supabase + iMac M1
1. 기존 정적 게임/Cloudflare Pages는 유지하고, Supabase(Auth/DB + 필요시 Edge Function 또는 원자적 Postgres RPC)를 신원·5판·광고 보상·검증 기록·랭킹 원본 저장소로 권장. Cloudflare Worker는 프록시/비밀키 보관/검증 등 실질 필요가 있을 때만 추가. Render 별도 상시 서버는 기본 설계에서 제외.
2. Supabase 실제 무료 프로젝트 수와 기존 변전현장대응 프로젝트 사용 상태를 확인. 기존 앱의 데이터/권한과 분리. 별도 프로젝트 생성 가능하면 독립 프로젝트, 불가하면 별도 스키마·RLS·권한 격리와 무료 용량을 검토해 선택. 기존 데이터 변경/삭제 금지.
3. 권장 테이블: \`profiles(user_id,nickname,created_at)\`, \`daily_quotas(user_id,kst_day,free_used,bonus_available)\`, \`game_sessions(id,user_id,kst_day,started_at,ended_at,status,game_version,server_seed)\`, \`ad_reward_events(unique_event_id,user_id,verified_at,provider)\`, \`verified_scores(session_id,user_id,kst_day,final_equity,profit,rate,verified_at,proof)\`. 서버 UTC timestamp 보관 후 KST 날짜 파생. 중복키·index 설정, RLS 기본 거부, 서버 함수 외 quota/검증점수 쓰기 차단.
4. API: registerNickname/getQuota/startSession/verifyReward/submitSession/getDailyTop5 및 관리자 점검. 시작 승인·횟수 차감은 트랜잭션 원자 처리. \`session_id\`와 요청 멱등키로 재시도 이중 소비 방지. service-role 키는 브라우저/Android 번들/GitHub 저장소에 절대 노출 금지. 필요시 함수 비밀저장소 사용.
5. 읽기 순위는 짧게 캐시 가능하지만 점수/횟수 갱신은 캐시로 판정 불가. 실제 무료 사용량·MAU·DB 크기·함수 실행량·egress와 Supabase 휴면 정책을 확인. 무료 목표는 가능하나 무료 유지·무중단을 보장하지 않는다.
6. iMac M1은 Tailscale/SSH 원격 관리, 암호화된 DB 백업, 복원 테스트, 비정상 랭킹 분석 및 장애 알림을 맡는다. 운영 랭킹/API/인증의 유일한 호스트로 두지 않으며 아이맥 절전·정전에도 클라우드 핵심 기능을 제공. iMac이 잠들어도 서버 유지되는 설계. 민감한 토큰은 iMac 키체인/안전한 Secrets에만 저장.

## H. Supabase Free Keepalive / 휴면 및 장애 대응 — 반드시 구현
1. Supabase 공식 안내상 Free 프로젝트는 **최근 7일간 DB 사용자 활동이 부족하면 일시정지될 수 있다**. 일정량의 실제 DB 요청이 도움이 될 수 있지만 정기 ping은 휴면 방지의 절대 보장이 아니다. 요금제/정책 변동 시 재확인. 긴급한 상시 가동 보장이 필요하면 유료 전환을 검토한다.
2. 기존 변전현장대응 프로젝트에서 사용한 Keepalive가 실제 존재·작동하는지 **GitHub Actions 워크플로·실행 로그·Secrets·Supabase RPC로 직접 점검** 후 구조만 재사용. 다른 프로젝트 URL/키를 그대로 복사하지 않는다. 개인 비밀키를 로그/코드에 노출하지 않는다.
3. **1차 실행 주체는 GitHub Actions schedule**. 예: 한국시간 매일 09:10에 대응하는 UTC cron \`10 0 * * *\` (GitHub Actions cron은 UTC 기준으로 명시). \`workflow_dispatch\` 수동 테스트 제공. scheduled run 지연/누락/비활성화될 수 있음을 고려하여 매일 최근 실행 및 성공 시각 모니터링. 사용자가 원하면 iMac M1 launchd를 **보조 확인용**으로 두되, Mac이 잠들었을 때 Keepalive가 실패하는 단일 의존 구조로 만들지 않는다.
4. **실제 PostgreSQL 활동**을 유발하는 최소권한 RPC \`keep_alive\` 또는 전용 \`healthcheck\` 테이블에 간단한 조회·소량 upsert를 구현. 데이터베이스 액세스가 확인되는 REST RPC/실제 SELECT/UPSERT를 사용하고 HTTP 홈페이지 GET, \`/auth/v1/health\`, API 게이트웨이 200 응답만으로 성공 판정 금지. DB에 불필요한 무제한 로그 행을 쌓지 않는다(고정 행 upsert 또는 경량 읽기). 로우 레벨 DB 권한은 꼭 필요한 범위만 허용.
5. 요청 타임아웃 10~20초, 3회 이내 지수 백오프 재시도 및 실패 시 잡 실패 처리. HTTP 200뿐 아니라 JSON 응답 또는 기록의 예상 DB 값까지 확인하여 성공 판정. 401/403 인증실패, 404 엔드포인트/테이블 누락, 429 제한, 5xx 장애, 540 paused 구분.
6. GitHub Actions 암호화 Secrets에 프로젝트 URL 및 전용 최소권한 키 등록. 공개 env나 앱 클라이언트에 서비스 역할 키 사용 금지. 프로젝트 키 교체 시 새 키 검증 후 기존 키 폐기. 워크플로 권한은 \`contents: read\` 등 최소.
7. 실행 로그에 시작/끝 KST 시각, 환경(운영/테스트), 결과, 응답코드(비밀 헤더 제외), DB 검증 상태, 마지막 정상 시각을 남긴다. **연속 2회 실패 또는 마지막 DB 성공 48시간 초과** 시 기존 사용자의 ntfy 등 승인된 알림 채널로 장애 통보(토픽·인증값은 Secrets). 성공 복구 시 정상화 알림, 실패를 성공으로 표시하지 않음. 기존 프로젝트와 알림 토픽 혼용 금지.
8. 운영 초기 직접 수동 실행 → DB 접속·실제 쿼리·로그 확인 → 다음 자동 실행 확인 → 의도적 인증실패 테스트로 경보 검증 → iMac 전원/절전과 무관함 검증. Supabase에서 경고 메일을 받거나 진짜 paused 상태면 **사용자에게 즉시 상태 알림**, 콘솔의 Resume project를 수행해야 할 수 있고 ping만으로 자동 해제된다고 단정하지 않는다. 확인되지 않은 복구 성공 주장 금지.
9. Keepalive의 목적은 소규모 서비스 운영·개발 중 휴면 가능성을 줄이는 것이며, 부하 유발이나 무료 정책 우회를 보장하는 도구가 아니다. 충분히 사용자 활동이 발생하는 경우 예약 쿼리 빈도를 재평가. 비용·무료 할당량 초과 모니터링 포함.
10. 검증 결과에 다음 네 가지를 반드시 기록: GitHub Actions 워크플로 URL, Supabase 프로젝트의 실제 DB 읽기/쓰기 성공 증거(민감정보 제외), 최근 7일 성공 이력, 실패 알림 테스트 결과. 하나라도 없으면 Keepalive 완료로 표시 금지.

## I. Play 스토어/Android 이미지 일치 및 릴리스
1. 사용자가 말한 Play Console '이미지 01'의 실제 파일·대상(스크린샷, 그래픽, 아이콘)부터 확인. 기존 채택 디자인 2번에 맞춰 **동일 문구·구도·색감**을 유지하고 임의 시안 새로 생성 금지. Play 이미지와 Android 런처 아이콘은 용도가 다르므로 원본 스타일만 일치시키고 각각 규격에 맞게 출력.
2. \`codex/scalping-king-android\` 및 \`scalping-king-android/store-assets\`, adaptive icon/foreground/background/monochrome/mipmap/round icon/splash, 실제 Play Console 원본, 설치된 앱 versionCode 비교. 최신 웹 리소스를 Capacitor Android에 복사·동기화하고 버전코드 올려 테스트 APK/AAB 재빌드.
3. 512×512 아이콘, 1024×500 배너, 1080×1920 스크린샷 5장의 문구·이미지 깨짐·정확한 크기와 실기기 표시 여부 검사. 실제 Play 등록 파일을 볼 수 없으면 단정하지 말고 확인 필요 항목으로 남긴다.
